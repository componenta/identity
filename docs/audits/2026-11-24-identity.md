## Подтверждённые дефекты и исправления

| Дефект | Основание | Исправление |
| --- | --- | --- |
| Повтор UUIDv1/v6/v7 при клонировании прогретой фабрики | Реальный публичный clone, фиксированное время, совпадающие строки | Для v1/v6 новый node/sequence, для v7 свежий rand_b |
| Повтор при fork | Реальный pcntl_fork после прогрева, фиксированное время и унаследованное состояние | Изоляция v1/v6 по PID; свежий CSPRNG rand_b для каждого v7 |
| Повтор при восстановлении фабрики | serialize/unserialize исходной фабрики, одинаковое время | Сериализуется конфигурация версии, не живое состояние. Старый сериализованный формат принимается, состояние не воспроизводится |
| Предсказуемые соседние v7 | Исходный rand_b инкрементируется вместе с rand_a | RFC 9562 § 6.2 method 1: 12-битный счётчик, новый 62-битный случайный хвост на каждый UUID |

| Частичная публикация v7-состояния при отказе CSPRNG | Старый алгоритм обновлял поля до завершения random calls | Вычисление в локальных переменных, публикация состояния только после успешной генерации |
| Нарушение инвариантов Uuid при native unserialize | Конструктор не вызывается: длина bytes, version и variant могли не соответствовать друг другу | __wakeup проверяет наличие и согласованность полей, сохраняя формат валидных объектов |

## RFC и границы ответственности

- v1: Gregorian epoch, 60-битная отметка, 14-битный clock_seq, 48-битный node, сетевой порядок байтов. Случайный node имеет установленный multicast bit (§ 6.10), реальный MAC не используется. Контрольный вектор A.1.
- v3/v5: MD5/SHA-1 по бинарному UUID namespace и точным байтам имени с правильной установкой версии/варианта. Контрольные векторы A.2/A.4. Эти алгоритмы обязательны для соответствующих UUID-версий и не заменяются другой хеш-функцией под тем же номером. Они не обеспечивают современной криптографической стойкости к коллизиям.
- v4: 122 случайных бита, фиксированные version/variant; A.3.
- v6: правильная перестановка 60-битной отметки; A.5. RFC § 5.6 разрешает сохранение node/clock_seq по модели v1, хотя рекомендует новые случайные значения для v6. Текущее документированное поведение стабильного node/sequence в одном процессе оставлено. Это не требование каждый раз менять node.
- v7: Unix milliseconds, 48-битный timestamp, 12-битный rand_a dedicated counter, 62 свежих случайных бита. A.6 проверяет кодирование полей. Повтор и откат времени используют предыдущую логическую отметку; переполнение счётчика увеличивает её, как допускает § 6.2. Последовательность не гарантирует глобального порядка между фабриками. Значение timestamp может опережать физическое время.
- v8: custom_a 48, custom_b 12, custom_c 62 бита, правильные version/variant. Входные границы и иллюстративные B.1/B.2 проверены. Уникальность пользовательских данных не гарантируется библиотекой.
- Nil, Max, зарезервированные варианты и неизвестные версии должны быть представимы UUID value object. Успешный парсинг не означает, что значение было сгенерировано по одному из RFC-алгоритмов. Свойство version является интерпретируемым номером версии только для соответствующего варианта.
- Отсутствие UUIDv2 не является неполной реализацией RFC 9562: алгоритм DCE Security не определяется этим RFC.
- Сохранено существующее нормализующее поведение fromString (в том числе trim и lowercase). Не превращать его без отдельного решения в строгий валидатор исходной строки.
- Не считать UUID секретом или основанием авторизации (§ 8). Для случайных идентификаторов подходит v4; для секретных токенов нужен отдельный криптографический механизм.

## Производительность и ограничения

Локальный ориентировочный микробенчмарк PHP 8.4.24, OPcache CLI по умолчанию, 7 серий по 100000 генераций на экземпляр, прогрев 10000, сравнение в обоих порядках:
- v7: 0.8253 → 1.0715 мкс в первом прогоне; 0.8929 → 1.0769 мкс во втором. +20–30% времени; абсолютная цена около 0.18–0.25 мкс на генерацию.
- v1/v6: заметные затраты проверки PID и диапазона. В первом прогоне 0.7620 → 0.9405 и 0.7571 → 0.9693 мкс соответственно. Во втором 0.6627 → 0.8637 и 0.8066 → 0.9191.
- v4 не менялся; его разброс между прогонами показывает, почему небольшие различия нельзя интерпретировать как доказанный выигрыш.

Не отменять свежую энтропию или границы времени для улучшения микробенчмарка. Будущая оптимизация требует повторяемых измерений и равнозначных контрактов.

Абсолютную глобальную уникальность нельзя доказать нагрузочным тестом. Для UUIDv7 при совпадающих timestamp и counter остаётся 62-битное случайное пространство; для UUIDv4 — 122 случайных бита. При большом количестве независимых генераторов вероятность зависит от числа значений в каждом общем префиксе, а не просто от общего числа UUID. Обеспечить уникальные индексы/обработку конфликтов там, где повтор недопустим. Не использовать UUID как security capability. Stateful factory не предназначена для одновременного использования несколькими потоками без синхронизации. Сериализованная фабрика — новый генератор, не способ продолжить монотонную последовательность. Не обещается защита от произвольного копирования состояния целой VM или компрометации OS CSPRNG. Не применять unserialize к недоверенным данным.

Ограничения аудита: не проводилась отдельная проверка Windows, 32-битной платформы (стандартный генератор явно требует 64-bit), mutation analysis, формальная проверка алгоритма или полноценный аудит всех приложений-потребителей. Не проверена реальная интеграция исправленного пакета с ещё не выпущенным DI 6; существующий тест ConfigProvider проходит. Изменение публичных сигнатур для генерации с ClockInterface не требуется и не выполнено.

## Следующее действие

В v1.0.1 есть подтверждённые дефекты; использовать для CQRS 5 следует новую исправленную стабильную версию Identity после релиза и интеграционной приёмки. CQRS-спецификацию обновить до новой минимальной версии после её публикации. Не менять время в UUID или архитектуру CQRS в данном аудите.
