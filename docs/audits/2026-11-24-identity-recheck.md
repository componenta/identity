## 1. Подтверждённые проблемы и исправления

| Обнаруженное поведение | Оценка | Исправление |
| --- | --- | --- |
| В v1 физический откат часов не менял clock_seq | Усиление соответствия § 5.1; прежний монотонный timestamp предотвращал локальный повтор | Раздельное хранение последнего успешного физического чтения и логической отметки. Изменение 14-битной последовательности при откате, включая wrap; равный физический tick не меняет sequence |
| v6 сохранял одинаковые node и sequence для многих UUID | Допустимая RFC альтернатива, но не предпочтительная рекомендация § 5.6 | Новые 61 случайный бит для каждого UUIDv6: 14 sequence + 47 node, установлен multicast bit. Нет коррелированного повторения хвоста |
| v1/v6 изменяли lastGregorianTicks до успешного получения энтропии | Воспроизводимый дефект восстановления при отказе, особенно на верхней границе timestamp | Commit состояния только после успешной генерации; при отказе сохраняется предыдущая успешно использованная отметка |
| В исключение парсера попадал полный произвольный input | Риск утечки, внедрения управляющих символов в журнал и лишнего расхода памяти | Ограниченное постоянное сообщение, тип исключения сохранён. Не гарантия отсутствия аргументов в логах/стеке приложения |
| Native unserialize мог сохранить ссылки на readonly bytes, version и variant | Воспроизводимое нарушение инвариантов | __serialize/__unserialize сохраняют валидный старый формат, проверяют согласованность и создают состояние из значений, не гидратируют ссылки в свойства |

Локальный RED/GREEN: первые пять сценариев (clock_seq, v6 random tail, отдельно v1 и v6 entropy failure, parser message) падают на исходной ревизии и проходят после исправления. Проверены Git blob SHA обоих основных файлов исходной ревизии (UuidFactory bf3c63008f894633507e3d001d59409062497e49, Uuid 8713d702bea826295c36147ebf671c1e84603a90) и итоговых файлов (UuidFactory 053e10d276ec7cdad90f7ae0ad95c8bdec1613ca, Uuid 98edc30d241e89fb3c34becf0eec3780d0e87471). Валидное старое сериализованное представление побайтно совпадает.

Прежние 16 локальных регрессий и обе программы нагрузочной генерации прошли на итоговом коде. Отдельные проверки не являются сертификатом безопасности PHP unserialize: никогда не применять его к недоверенному вводу.

## 2. Матрица RFC 9562

| Норма / рекомендация | Результат |
| --- | --- |
| § 4: 16 октетов, big-endian, hex-and-dash, upper/lower/mixed case | Реализация и round trip корректны; парсер дополнительно сохраняет историческое trim-поведение, не является строгой проверкой исходного wire-format |
| §§ 4.1–4.2: поля варианта и версии | Проверены все 256 возможных октетов варианта и 16 версионных полубайтов (4096 комбинаций). Для зарезервированных вариантов поле version — сырое значение, а не подтверждение RFC-версии |
| § 5.1: Gregorian epoch, time_high, random initial sequence, rollback, node | Правильная упаковка и диапазон, random_int/random_bytes, изменение sequence при физическом rollback, multicast bit, нет MAC. v1 timestamps монотонны; строковая сортировка v1 не обещается |
| § 5.2: DCE Security | Генерация v2 не реализуется, поскольку алгоритм вне области RFC. Представление таких UUID не запрещено |
| §§ 5.3, 5.5, 6.5–6.6: name-based | Точные MD5/SHA-1 и сетевой порядок UUID namespace. Имена — произвольные байты; выбор их канонического представления на вызывающей стороне. Векторы RFC и независимые векторы Python; пользовательский namespace поддерживается. v5 предпочтительнее v3, оба не для защиты от намеренных коллизий |
| § 5.4: UUIDv4 | 122 случайных бита, фиксированные поля версии/варианта, fail closed при ошибке энтропии |
| § 5.6: UUIDv6 | Перестановка времени и все поля корректны. Принята предпочтительная рекомендация обновлять sequence и node для каждого UUID |
| § 5.7: UUIDv7 | Время Unix в миллисекундах, default version v7, 12-битный счётчик method 1, 8-битный seed с запасом для rollover, свежие 62 случайных бита |
| § 5.8: UUIDv8 | Версия/вариант и поля 48/12/62, проверка входных размеров. Уникальность custom payload не обещается |
| §§ 5.9–5.10: Nil/Max | Корректно представимы и проверены |
| § 6.1: источники времени, точность, диапазон, overrun | Системное время, 100-нс логические ticks / миллисекунды; отсутствие тихого усечения; OverflowException на исчерпании. Отдельные тесты нижней/верхней границ |
| § 6.2: монотонность, счётчики, rollover | v6/v7 строго упорядочены в отдельном экземпляре, обработаны одинаковые и уменьшающиеся отметки. При переполнении счётчика v7 логическое время увеличивается. Это разрешённый вариант, не обещание точного физического времени |
| §§ 6.3–6.4: состояние и distributed generation | In-memory состояние, сохранение конфигурации версии при сериализации, не replay рабочего состояния. Координация и постоянное хранилище необязательны; нет глобальной гарантии |
| §§ 6.7–6.9: collision resistance, randomness | Native OS CSPRNG. Не использовать слабые источники при сбое; реальные fork и clone regression. v1 обновляет state при смене PID, v6/v7 используют свежую энтропию. Не утверждать математическую невозможность коллизий |
| § 6.10: privacy | Случайные multicast node вместо MAC, проверено битовое кодирование |
| §§ 6.11–6.13: sorting, opacity, DB | Сетевой порядок, сравнение байтов, v6/v7 ordering, рекомендации хранения 16 байт и уникальных ограничений. Не извлекать доверенное время/право доступа из UUID |
| § 7: IANA | Четыре predefined namespace совпадают с RFC 9562 и IANA. Enum не претендует на полноту обновляемого реестра, дополнительные UUID namespace принимаются через UuidInterface |
| § 8: security | UUID не capability/token и не доказательство подлинности. v4 предпочтителен, если UUID нужен в security operation, права проверяются независимо. Нет MAC, нет слабого PRNG; предупреждения MD5/SHA-1 и custom v8 задокументированы |

Не все рекомендации относятся к универсальной библиотеке. Например, требование уникальности в конкретной БД, синхронизация распределённых узлов, политика выбора канонического имени и проверка прав являются ответственностью приложения. Нет оснований вводить центральный registry, персистентный глобальный генератор или новый публичный интерфейс.

## 5. Ограничения и готовность

- Не обещается абсолютная уникальность. В v7 при совпадающем timestamp/counter условное пространство — 2^62; в v4 2^122. Для v6 новые 61 случайный бит на timestamp. В v1 начальные node/sequence также дают 61 случайный бит, но сохраняются между генерациями до изменения состояния; это не 61 независимый бит для каждого v1.
- При экстремальном масштабе/критичности коллизий применять уникальные ограничения и обработку конфликтов; для высоконадёжных распределённых схем нужны отдельные требования.
- Stateful factory не reentrant и не thread-safe; независимые экземпляры или внешняя синхронизация. Не гарантируется устойчивость при компрометации CSPRNG или клонировании всей VM/OS.
- UUID не секрет, не токен доступа и не достоверный timestamp. Native PHP unserialize только доверенного содержимого.
- 32-bit для генератора не поддерживается; 32-bit value objects, macOS, mutation testing и формальная криптографическая верификация не выполнялись. На PHP 8.6 проверен production consumer, не полный PHPUnit. На Windows PCNTL отсутствует.
- Совместимость сигнатур сохранена, но новые v6 обновляют ранее стабильные поля, v1 меняет sequence при откате, сообщения парсера не отражают вход, сериализованный UUID восстанавливается без ссылок. Это намеренные изменения поведения безопасности. Сериализация валидных UUID сохранена побайтно.
- Не использовать старый релиз v1.0.1 для миграции CQRS. По результатам повторной приёмки проверенный код готов к отдельному стабильному релизу при сохранении указанных ограничений. Стабильный DI 6 после публикации следует проверить в интеграции CQRS; текущая CI проверка подтверждает конкретный snapshot. Новые архитектурные изменения не требуются.
